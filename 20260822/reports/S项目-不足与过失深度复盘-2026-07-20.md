# S项目（SellerAI）不足与过失深度复盘

**日期**: 2026-07-20  
**作者**: 参谋长（基于全量审计+历史MEMORY+代码库深度扫描）  
**用途**: 创始人内参 — 让 R 项目不踩同一个坑  
**原则**: 不粉饰、不自洽、不推锅。每个问题写清"如果重来怎么做"。

## 一、产品层面过失

### 1.1 功能膨胀 — MVP 沦为"什么都想做"

| 问题 | 具体表现 |
|:----|:--------|
| **加了不该加的功能** | 博客系统（4+篇SEO文章+[slug]动态路由）、国际化脚手架（EN/DE/FR/ES/中文/JA/IT/PT/KO/NL 共10种语言）、多工具页面（Keyword Tool + Listing Scorer + Profit Calculator + Export Tool）、ResourceCenter、ChinaBuyerGuide |
| **根因** | MVP 意图不明。"能加就加"替代"只做核心价值证明"。每次 git commit 都在加新东西，从不删东西。没有功能冻结线。 |
| **后果** | 前端重构 3 次：组件反复增减（从 21 个组件到删除再添加）。浪费 ~2 天开发工时。commit 历史从 v1 核心功能（9957eef）膨胀到多语言（10ae911）、多工具（98dc917）、再被审计发现语言切换器不可用（P1-10）。 |
| **如果重来** | MVP 只做 3 个页面：Landing → 生成器 → 定价。博客/多语言/多工具全部砍掉，等有 50 个付费用户再评估。 |
| **R 项目避免方式** | **功能冻结 2 周**：Landing + 核心功能页 + 定价。任何新功能提议必须经过"这个功能能帮我们多赚 $1 吗？"测试。 |

### 1.2 定价混乱 — 反复横跳 3 次

| 问题 | 具体表现 |
|:----|:--------|
| **价格路径** | $19.9/月 → $14.9/月(Founder) → $19.9/月+$199/年。同一个 Pricing 组件里三套价格并存（实测代码中 `$19.9`、`$199`、`$14.9` 全部出现在同一文件）。Blog 中还残留着 "$29/mo" 的错误文案（P1-2、P1-11）。 |
| **根因** | 没做充分调研就拍板。定价是靠直觉改的，不是靠数据定的。没有做过竞品对标（竞品卖多少？用户愿意付多少？），也没有做过用户分段定价测试。 |
| **后果** | 前端改 3 次、Gumroad 商品重做 2 次（旧 slug `/l/sellerai` 已删，新 slug `/l/kajyx` → 旧链接全部断链）。Blog 中出现矛盾定价信息，影响品牌信任。 |
| **如果重来** | 上线前做竞品调研（至少看 5 个竞品价格），选定一个价格锁死不改。100 付费用户前任何调价动议直接拒绝。 |
| **R 项目避免方式** | **一次钉死**：$9.9/月 Free→Pro→Enterprise 三级。上线前竞品对标完成。100 付费用户前不改价。 |

### 1.3 用户流程不闭环 — 每一步都有断点

| 环节 | 断点 | 后果 |
|:----|:----|:-----|
| **注册** | 邮箱验证码登录流程能走通，但 LoginModal 在移动端溢出可视区域（`items-start` + 无滚动限制），用户看不到完整登录表单 | 移动端用户流失 |
| **激活** | License 激活 API 存在但流程绕：用户需在 Gumroad 购买后手动输入 license key → 调用 `/api/activate-license`。无自动关联（需手动匹配邮箱） | 付费用户卡在激活环节 |
| **使用** | 配额显示混乱：QuotaBadge 用 `fixed top-3 right-14` 定位，在移动端遮挡按钮；FAQ 写"每月3次"实际"每天3次"（P0-2） | 用户困惑 → 放弃使用 |
| **付费** | FAQ 写"monthly limits" → 实际是 daily limit；Pricing 组件写"Monthly $19.9/mo"但 FAQ 暗示还有 monthly tier quota；Blog 写 $29/mo → 用户完全不信任 | 转化率极低 |
| **留存** | 无 trial 系统（注册后直接 free/paid 二选一），无 onboarding 引导，无使用后 follow-up 邮件 | 一次用完就走 |

| **根因** | 各模块独立开发，没有人做全流程走查。开发盯着自己的组件，没有人从"用户怎么找到我们的 → 怎么注册 → 怎么用 → 怎么付钱 → 怎么留下来"走一遍。 |
| **如果重来** | 上线前创始人亲自用手机走完一遍全流程，记录每个卡点。每个断点 P0 阻塞直到修好。 |
| **R 项目避免方式** | 上线前做全流程走查清单。第一版就带 trial（3-7 天无限试用）。所有文案与代码逻辑强制同步检查。 |

### 1.4 文案与产品不一致 — 自我矛盾 3 处

| 问题 | 位置 | 具体 |
|:----|:----|:-----|
| P0-2 | FAQ.tsx vs lib/quota.ts | FAQ 写"每月3次"→ 代码"每天3次" |
| P1-2 | Pricing.tsx vs lib/blog.ts | Pricing 写 $19.9 → Blog 写 $29 |

| **R 项目避免方式** | FAQ 文案从 `config.ts` 常量导出，保证单一事实来源。上线前做"文案-代码一致性走查"。 |

## 二、技术层面过失

### 2.1 部署路径三换 — 浪费 3 天

| 路径 | 时间 | 失败原因 |
|:----|:----|:--------|
| Vercel | Day 1 | 个人 token 无 team 写入权限 → 403 |
| Netlify | Day 2 | 同上，team 下个人 token 无写入权限 |
| Cloudflare Workers | Day 3 | ✅ 最终解法（OpenNext 适配器 + wrangler deploy） |

| **根因** | 没一次性调研透。Vercel/Netlify 的 team 权限模型是已知问题，调研 5 分钟就能发现。直接跳 CF Workers 才是正确路径。 |
| **后果** | 浪费 ~3 天，域名 DNS 反复改（NS 从 DNSPod → Vercel DNS → Cloudflare NS），期间出现过 530/10000 错误。 |
| **如果重来** | 花 2 小时写一个"部署选项对比表"再动手。已知条件：个人免费账户、自定义域名 → 直接排除 Vercel/Netlify。 |
| **R 项目避免方式** | 已定 CF Workers，不改。但教训是：任何基础设施选型，先做 2 小时 due diligence 再动手。 |

### 2.2 安全漏洞 — 3 个 P0

| 漏洞 | 审计编号 | 具体 |
|:----|:--------|:-----|
| Webhook 无签名验证 | P0-1 | `GUMROAD_WEBHOOK_SECRET` 未设置时静默放行所有请求 → 任何人都可以伪造购买事件 |
| Token 明文存库 | P0-3 | `auth_tokens` 表存原始 token → D1 被攻破 = 所有用户会话可劫持 |
| Secrets 文件暴露风险 | P1-8 | `secrets/gumroad.txt` 明文存 webhook secret，`.gitignore` 未排除 `secrets/` 目录 |

| **根因** | 赶上线跳过安全检查。审计发现 23 个问题中 6 个是安全问题，上线的代码没有经过任何安全审查。 |
| **后果** | 存在伪造 webhook 攻击风险（免费激活/恶意撤销）。Token 明文存储意味着任何有 D1 访问权限的人（包括 CF Dashboard 登录者）都能劫持所有会话。不可量化但严重。 |
| **如果重来** | 上线前强制安全检查清单：webhook 签名验证 → hash token → 排除 secrets 文件 → CORS 白名单。不是"先上线再修"，是"不修好不上线"。 |
| **R 项目避免方式** | 直接复用修复版（签名验证已加、SHA-256 token hash 已实现、secrets 目录已排除）。但新增：上线前 P0 安全检查通过才算"可以上线"。 |

### 2.3 Codex 反复 — 策略不坚定

| 时间 | 决策 | 来源 |
|:----|:----|:-----|
| 2026-07-16 | 编码禁用外部付费 Codex | MEMORY.md 铁律 |
| 2026-07-18 23:50 | Codex 接入团队（编码/高难任务可用） | 创始人拍板反转 |
| 2026-07-19 10:00 | Codex 接入叫停 | 创始人再次拍板反转 |

| **根因** | 没有在开工前想清楚"我们用哪个模型做主力"这个根本问题。在"省钱"和"追求质量"之间摇摆。 |
| **后果** | 团队策略混乱。期间可能有人按 Codex 模式工作、有人按 DeepSeek 模式工作。 |
| **如果重来** | 开工第一天定模型策略，铁律执行 2 周不变。2 周后根据数据复盘再调。 |
| **R 项目避免方式** | **全程 DeepSeek**。不接入 Codex、Claude、GPT 等外部付费模型。用数据说话：DeepSeek ¥0.006/次，质量够用，不必为"可能更好"买单。 |

### 2.4 浏览器操控失败 — 技术选型不成熟

| 问题 | 具体表现 |
|:----|:--------|
| **CDP 会话冲突** | 3 个 Agent 同时抢同一 CDP 9222 端口，互相干扰 → 乱发重复帖、覆盖对方操作 |
| **ref 过期死循环** | xbrowser snapshot 返回的 ref 在 DOM 刷新后失效 → 死循环重试 |
| **contenteditable 不可靠** | Reddit 发帖框是 contenteditable div → 标准 input fill 不生效 → 需要坐标点击 + 逐字键入 |
| **有头模式必崩** | Edge 有头可视化模式在此环境必崩（exit code 0），Chromium 版本不兼容 |

| **根因** | 浏览器自动化（browser automation）本身是不成熟的技术路线。CDP 协议设计给 DevTools 用的，不是给多 Agent 并发用的。 |
| **后果** | 数小时浪费在调试浏览器操作上。Reddit 发帖 1 条成功背后是几十条失败尝试。 |
| **如果重来** | 第一天就放弃浏览器自动化做推广。用 API 发帖或无头 HTTP 请求。浏览器只用来做一次性视觉验收。 |
| **R 项目避免方式** | **全 API 路线**。不做任何浏览器自动化发帖。推广走 ProductHunt API + SEO 自然流量 + Twitter/X 冷启动。 |

### 2.5 其他技术过失

| 问题 | 审计编号 | 描述 |
|:----|:--------|:-----|
| 配额检查 fail open | P1-3 | D1 故障时所有请求无限制通过 |

| 安全头缺失 | P2-1 | 无 CSP/HSTS/X-Frame-Options |

| **R 项目避免方式** | 上线前跑一遍完整审计（复用本次审计框架）。所有 P1+ 必须在上线前修完。 |

## 三、推广/获客层面过失

### 3.1 Reddit 养号失败 — 不懂规则就执行

| 问题 | 具体表现 |
|:----|:--------|
| **新号直接发推广** | 创始人 2026-07-16 要求"团队全权自动发帖"。子 Agent 拿到指令就在 Reddit 新账号上直接发推广帖 → 被机器人秒删/判广告 |
| **创始人 7/17 介入叫停** | 改为"养号 3-7 天，先评论攒 karma" |
| **养号也出问题** | 同一个 CDP 会话被 3 个 Agent 抢，导致乱发重复帖 |
| **最终放弃** | 7/19 复盘结论：R 项目不做 Reddit 推广 |

| **根因** | 不懂平台规则就执行。Reddit 新号发外链 = 100% 被删，这是常识。团队没有做"发帖前风险预判"（违反 7/16 23:07 铁律）。 |
| **后果** | ~3 天零获客。Reddit 账号权重受损（即使后续养号也难恢复）。 |
| **如果重来** | 派推广子 Agent 之前，先让它输出一个"平台规则调研 + 风险预判"文档。确认后再发。 |
| **R 项目避免方式** | **不做 Reddit 推广**。改为 ProductHunt 首发 + SEO 自然流量 + Twitter/X 冷启动。 |

### 3.2 创始人无受众认识延迟 — 浪费 1 天走错方向

| 时间 | 认知 | 后果 |
|:----|:----|:-----|
| 7/16 23:19 | 团队假设创始人"有群/朋友圈/私域渠道" | 制定"群转发/群机器人 webhook"方案 |
| 7/17 09:53 | 创始人澄清："我现在什么都没有" | 推翻全部方案，重新设计获客路径 |

| **根因** | 没先做用户调研。默认"创始人应该有一些渠道吧"→ 实际"什么都没有"。 |
| **后果** | 方案方向错了 ~1 天。如果第一天就问清楚，那 1 天的精力可以放在 SEO 或 ProductHunt 准备上。 |
| **如果重来** | 开工前第一件事：确认创始人现有资源清单（受众/渠道/社群/可触达人群）。 |
| **R 项目避免方式** | 上线前先确认创始人现有流量池（大概率还是没有），以此为起点设计获客。 |

### 3.3 推广策略混乱 — 没统一方案就四处出击

| 阶段 | 策略 | 结果 |
|:----|:----|:-----|
| 第 1 天 | "全团队自转"（自动化发帖） | 不知道发什么、发到哪 |
| 第 2 天 | Reddit | 被删帖、被封 |
| 第 2 天 | 知乎/小红书/抖音/FB 多平台铺开 | 每个平台都碰壁（注册/验证/内容门槛） |
| 第 3 天 | 放弃多平台，回 Reddit 养号 | 精力耗尽 |
| 第 4 天 | 放弃所有社区推广 | 0 获客 |

| **根因** | 没统一策略。每个推广渠道都是"先试试看"→ 碰壁 → 放弃 → 换下一个。没有人在开工前写一份"推广方案"。 |
| **后果** | ~2 天无效试错。精力、算力、CDP 会话全部浪费。 |
| **如果重来** | 开工前先写好推广方案（目标渠道 + 内容类型 + 发布节奏 + 预期效果 + 风险），创始人拍板后执行。不做"边做边想"。 |
| **R 项目避免方式** | 上线前写好推广方案，一个渠道做透再开下一个。不做多平台同时铺。 |

## 四、流程/管理层面过失

### 4.1 审批阻塞 — 每步等创始人

| 问题 | 具体表现 |
|:----|:--------|
| **6 项 P0 阻塞未解决** | 从 7/16 上线到 7/20 审计，至少有 6 个 P0 级问题（部署路径、定价、推广渠道、安全漏洞、功能取舍、模型选择）每步都要等创始人决策 |
| **决策延迟 1-5 小时** | 每步等创始人回复 → 执行 → 再等 → 再执行 |
| **根因** | 没预设决策树。团队不知道什么级别的事可以自己做，什么才需要创始人拍板。所有事都推上去。 |
| **如果重来** | 预设 3 级决策树：L1（团队自主执行不汇报）、L2（团队先做方案再找创始人确认一次）、L3（创始人亲自决策）。L1 占 90%。 |
| **R 项目避免方式** | **预设决策树**。哪些是自主决策、哪些需确认一次、哪些必须创始人拍板——写在项目启动文档里。 |

### 4.2 子Agent 失控 — 无止损机制

| 问题 | 具体表现 |
|:----|:--------|
| **死循环 29 分钟** | 子 Agent 在同一个失效 ref 上反复重试 |
| **3 个抢同一浏览器** | 同一 CDP 9222 被 3 个 Agent 同时操作 → 互相覆盖 |
| **无超时自动 kill** | 子 Agent 没有硬超时限制，跑死了就死着占资源 |
| **根因** | 没设止损机制。派 subagent 没有 "max_attempts=1" 约束，没有超时自动 kill，没有浏览器独占锁。 |
| **后果** | 浪费算力和时间。7/17 多名子 Agent 同时在线抢资源。 |
| **如果重来** | 每个子 Agent 派之前设定：最多 1 次尝试、硬超时 10 分钟、失败直接回报"无法完成"。 |
| **R 项目避免方式** | **1 次尝试铁律**。子 Agent 不允许重试。失败即回报。|

### 4.3 初期无成本核算 — 第 2 周才出完整账本

| 问题 | 具体表现 |
|:----|:--------|
| **7/16 才有成本核算** | 项目已经上线了，第 2 周才由成本控制部出完整的"每订阅净留存/边际收益/隐性开销/长期运维成本"账本 |
| **早期决策缺数据** | 定价、推广预算、功能投入等决策都是"凭感觉"做的 |
| **根因** | 没意识到要先算账。团队的组织架构里有"成本控制部"，但实际是先上线后算账。 |
| **后果** | 早期决策（如定价 19.9 vs 14.9、推广渠道选择）缺乏 ROI 计算支撑。 |
| **如果重来** | 开工第 1 天先出成本模型：固定成本、边际成本、盈亏平衡点、各渠道 CAC 估算、各定价的 ROI。 |
| **R 项目避免方式** | **开工前出成本模型**。不拿"先上线再说"当借口跳过核算。 |

### 4.4 团队私自执行 — 违反铁律

| 问题 | 具体表现 |
|:----|:--------|
| **7/17 Reddit 事故** | 子 Agent 拿到"发帖"指令就在 Reddit 新号上直接发推广帖，未经团队商讨，未出方案等创始人拍板 |
| **创始人 7/17 16:42 怒批** | "先做任何事情都要经过团队的考察再去做" |
| **7/16 豆包被开除** | 因私自做主（未过团队商讨就改 og:url、部署发版）被创始人开除 |
| **根因** | 子 Agent 把"拿到指令就执行"理解为"可以跨过商讨和审批"。创始人铁律（7/16 23:07）明确写了"所有提议必须先经团队商讨"，但执行中又走了"agent 自主执行"的极端。 |
| **如果重来** | 对外/用户可见动作必须走团队商讨 → 方案 → 等创始人 go。任何 agent 不得跳过。 |
| **R 项目避免方式** | 子Agent Task 开头强制写入："本任务所有对外/用户可见动作必须先输出方案并暂停，等创始人确认后再执行。" |

## 五、用户体验层面过失

### 5.1 移动端适配缺陷

| 问题 | 具体表现 | 审计编号 |
|:----|:--------|:--------|
| **LoginModal 溢出** | `items-start justify-center` 无滚动限制 → 小屏手机上登录表单超出可视区域，用户看不到完整表单 | 无编号（代码审计发现） |

| **R 项目避免方式** | 上线前必须在 375px 宽度（iPhone SE）上完成全流程走查。 |

### 5.2 中英文混用 — 不专业

| 问题 | 具体表现 |
|:----|:--------|
| **QuotaBadge 中英文混** | `Free 路 ${remaining} left` — 英文括号中文单位。日文假名出现在英文界面 |
| **关闭按钮乱码** | QuotaBadge 面板关闭按钮显示 `脳`（日语片假名），而非标准 `×` |
| **Footer/CTA 中英文杂** | 部分面向中国卖家的文案（ChinaBuyerGuide）全中文夹在英文站点中 |

| **根因** | 文案未经统一审核。不同人在不同时间写的文案，没有统一的 tone of voice 和语言规范。 |
| **如果重来** | 定一条铁律：面向页面只允许一种语言，不做中英混排。所有文案上线前由一个人通读一遍。 |
| **R 项目避免方式** | **英文统一**。不做中英文混合页面。所有 UI 文案从单一 `en.json` 或配置常量导出。 |

### 5.3 FAQ 与实际不符 — 用户误导

| 问题 | 审计编号 | 描述 |
|:----|:--------|:-----|
| FAQ 写"每月3次" | P0-2 | 代码实际"每天3次" |

| **根因** | 代码改动了配额逻辑（daily limit），FAQ 没同步更新。文案和代码是两套系统，没有人负责同步。 |
| **如果重来** | 配额常量从 `const DAILY_LIMIT = 3` 导出，FAQ 文案用同一个常量动态渲染 `${DAILY_LIMIT} per day`。 |
| **R 项目避免方式** | FAQ 文案从配置常量自动生成，不手写。|

## 七、十大教训（按重要性排名）

### 🥇 第 1 条：MVP 不是功能堆砌，是"最少能验证付费意愿的东西"

S 项目加了博客、多语言、多工具、买家指南——没一个是验证"用户愿意为 AI Listing 付钱"所必需的。R 项目只做 3 页，多一个功能都不加，除非它能证明"这个功能会让用户多付 $1"。

### 🥈 第 2 条：定价是"先设后调"，不是"边调边改"

定价改 3 次不仅浪费开发时间，更重要的是让早期用户觉得你不靠谱。100 付费用户前锁死价格，任何调价动议直接拒绝。

### 🥉 第 3 条：安全不要事后补

webhook 无签名、token 明文——这些不是"上线后优化"的问题，是"上线前必须修"的问题。安全漏洞发现的代价远高于预防成本。

### 第 4 条：开工第 1 天就算清楚账

成本核算不应该是"第 2 周补做的作业"。不知道自己赚不赚钱、花多少钱、亏在哪，所有决策都是盲人摸象。

### 第 5 条：不懂平台规则就不要碰

Reddit 新号发推广帖 = 100% 被删，这是常识。在做任何推广动作之前，先花 30 分钟读平台规则。不懂就不碰。

### 第 6 条：浏览器自动化做推广 = 死路

CDP 协议给 DevTools 用的，不是给多 Agent 并发做推广用的。推广走 API 或无头 HTTP，浏览器只用来做视觉验收。

### 第 7 条：创始人资源零假设

不要假设创始人有群/有朋友圈/有受众。第一天就问清楚现有资源清单，以此为起点设计获客路径。

### 第 8 条：子Agent 必须设止损

没有 max_attempts=1、没有硬超时、没有浏览器独占锁 → 子Agent 会死循环 29 分钟、3 个抢同一浏览器。派之前设定止损，派出去不管。

### 第 9 条：文案和代码必须"单一事实来源"

FAQ 写"每月 3 次"、代码跑"每天 3 次"——因为文案是手写的，代码是常量。所有面向用户的数字必须从同一个配置常量导出。

### 第 10 条：上线前亲自走一遍全流程

创始人用手机从"用户怎么找到我们"走到"怎么付钱"，记录每个卡点。不修好不上线。
