## 三、中危问题（3个）

### 🔶 M1: `generate-listing` 的 CORS 配置存在潜在风险

**位置**: `app/api/generate-listing/route.ts`  
**问题**: `getAllowedOrigins()` 从环境变量读取，但 `evaluateOrigin()` 的 fallback 逻辑允许 `host === originHost` 通过——这意味着任何子域名或反向代理到同一 host 的请求都会被允许。

```typescript
// 当前代码
if (host && originHost === host) {
  return { allowed: true, effectiveOrigin: origin };
}
```

**风险**: 如果攻击者能通过 DNS 劫持或子域名接管指向同一 host，可能绕过 CORS 限制。

**修复建议**: 
```typescript
// 建议：严格白名单，移除 host 匹配 fallback
function evaluateOrigin(request, allowed, origin) {
  if (!origin) return { allowed: false }; // 无 origin 直接拒绝
  if (allowed.size > 0 && allowed.has(origin)) {
    return { allowed: true, effectiveOrigin: origin };
  }
  return { allowed: false, effectiveOrigin: origin };
}
```

**优先级**: 中  
**修复难度**: 低（改 1 处）

---

### 🔶 M2: `auth/register` 端点存在重复插入和令牌返回不一致

**位置**: `app/api/auth/register/route.ts`  
**问题**:
1. 第 45-55 行：同一个 INSERT 语句执行了两次（重复插入同一行）
2. 第 62 行：返回的 `token` 是 `rawToken`（明文），但数据库存的是 `hashedToken`——这是正确的做法，但注释说"JWT-like token"实际上不是 JWT，只是随机字符串
3. 端点没有 rate limiting，可被暴力注册

```typescript
// 问题代码：重复执行相同 INSERT
await db.prepare(...).bind(email, visitorId, trialEndsAt).run(); // 第1次
await db.prepare(...).bind(email, visitorId, trialEndsAt).run(); // 第2次（重复！）
```

**风险**: 
- 重复插入虽因 `OR IGNORE` 不会报错，但浪费 DB 操作
- 无 rate limit 可被用于批量伪造用户

**修复建议**:
1. 删除重复 INSERT
2. 添加 `checkRateLimitD1` 调用
3. 考虑废弃此端点（当前主流程用 verify-code，register 端点似乎未被使用）

**优先级**: 中  
**修复难度**: 低

---

### 🔶 M3: `gumroad-webhook` 的 `raw_payload_hash` 可能不够唯一

**位置**: `app/api/gumroad-webhook/route.ts`  
**问题**: 使用 SHA-256 对 raw body 做 hash 存入 `raw_payload_hash`，但相同内容的 webhook 会产生相同 hash。如果 Gumroad 重发同一事件，无法区分是重发还是新事件。

**风险**: 幂等性依赖 `gumroad_sale_id`，但 audit log 中可能因 hash 相同而难以排查重发问题。

**修复建议**: 在 hash 中加入时间戳或 nonce，或直接存储完整 raw body 的加密版本（但考虑隐私）。

**优先级**: 中（设计权衡）  
**修复难度**: 中

## 四、低危/优化项（5个）

### 🟢 L1: `send-code` 的验证码生成算法不够均匀

**位置**: `app/api/auth/send-code/route.ts`  
**问题**: 
```typescript
const num = parseInt(uuid.slice(0, 6), 16) % 1000000;
```

取 UUID 前 6 位 hex（24 位随机）mod 1000000，分布足够均匀，但不如直接用 `crypto.getRandomValues` 生成 6 位数字直观。

**风险**: 极低，24 位熵足够安全  
**建议**: 保持现状或改为 `Math.floor(Math.random() * 900000) + 100000`（但 crypto 更安全）

---

### 🟢 L2: `verify-code` 的 `recordVerifyAttempt` 在成功时 DELETE 整条记录

**位置**: `app/api/auth/verify-code/route.ts`  
**问题**: 成功验证后 `DELETE FROM verification_attempts WHERE email = ?`，丢失了历史审计数据。

**建议**: 改为 UPDATE 重置 attempts=0，保留记录用于审计。

---

### 🟢 L3: `quota.ts` 的 `ensureVisitorRow` 存在 SQL 注入风险（理论上）

**位置**: `lib/quota.ts`  
**问题**: 所有 SQL 都使用参数化查询（`?` 占位符），实际上没有注入风险。但 `userEmail` 直接传入 `ensureVisitorRow` 后用于 `bind()`，如果上游未校验 email 格式，极端情况下可能传入恶意字符串。

**现状**: 实际上安全（D1 参数化查询天然防注入）  
**建议**: 在 `ensureVisitorRow` 入口添加 email 格式校验作为防御性编程。

---

### 🟢 L4: 日志中可能泄露敏感信息

**位置**: 多处 `console.error`  
**问题**: 
- `generate-listing` 的 error 日志可能包含用户输入的 description
- `gumroad-webhook` 的 error 日志包含 raw body 信息
- `send-code` 的 error 日志包含 email 地址

**建议**: 
- 生产环境关闭 debug 日志或脱敏处理
- 使用结构化日志，标记敏感字段

---

### 🟢 L5: `wrangler.jsonc` 中 `RESEND_FROM_ADDR` 使用测试域名

**位置**: `wrangler.jsonc`  
**问题**: 
```json
"RESEND_FROM_ADDR": "SellerAI <onboarding@resend.dev>"
```

`onboarding@resend.dev` 是 Resend 测试域名，只能发给发信人自己的邮箱。真实用户收不到验证码。

**状态**: 已知问题，之前已排查确认  
**修复**: 需要创始人登录 Resend 后台验证 `sellerai.listaikit.com` 域名，然后更新 `RESEND_FROM_ADDR`

## 五、安全设计亮点 ✅

| 设计 | 位置 | 说明 |
|------|------|------|
| **Token 哈希存储** | `crypto.ts` | 明文 token 永不入 DB，只存 SHA-256 hash |
| **Fail-Closed 设计** | `generate-listing` | 无 DB/无认证/无配额 = 直接拒绝 |
| **原子操作** | `quota.ts` | 所有配额扣减用单条 UPDATE，无竞态条件 |
| **D1 持久化限流** | `rateLimitD1.ts` | 限流状态持久化，不受冷启动影响 |
| **HMAC 签名验证** | `gumroad-webhook` | Gumroad webhook 带 HMAC-SHA256 签名验证 |
| **TOCTOU 安全** | `founders.ts` | 创始人名额用单条 UPDATE 原子抢占 |
| **授权码顶号机制** | `redeem-code` | 同码重复兑换吊销旧 token，防转卖 |
| **限时卡到期** | `0011_timed_license.sql` | 30 天卡自动到期，不依赖 webhook |
| **IP 反滥用** | `quota.ts` | 同一 IP 每天最多 5 个新 visitor |
| **验证码限流** | `send-code` | 15 分钟内超 5 次发送自动封禁 15 分钟 |
