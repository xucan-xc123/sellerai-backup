## 第一章：核心评论爬虫技术方案（最核心技术模块）

> ReviewIQ 能否落地的关键。评论爬虫决定数据源质量，数据源质量决定 AI 分析深度。

### 1.1 方案比选

| 方案 | 优点 | 缺点 | 月成本 | 推荐程度 |
|:----|:----|:-----|:------|:--------|
| **A: 直接HTTP爬取Amazon评论页** | 免费、无依赖 | Amazon反爬严格（IP限频、CAPTCHA、DOM结构频繁变） | ¥0 | ❌不推荐单独用 |
| **B: 住宅代理池（Bright Data / IPIPGO）** | 稳定、可大规模扩展 | 贵、需配置代理轮换 | ¥80-500/月 | ⭐⭐⭐MVP可用 |
| **C: 第三方API（Rainforest API / Keepa API / ASIN Data API）** | 数据质量高、JSON返回、反爬交给他们 | 按次收费（$0.01/次） | $30-300/月 | ⭐⭐⭐⭐推荐 |
| **D: Amazon SP-API（需卖家授权）** | 官方数据、合法合规 | 需卖家授权、不是所有卖家都愿意给 | ¥0 | ⭐⭐⭐长期补充方案 |
| **E: 混合策略（一手用免费解析+备用代理池）** | 成本最优、反爬切换灵活 | 实现复杂 | ¥30-100/月 | ⭐⭐⭐⭐⭐**强烈推荐** |

### 1.2 混合策略(E)详细方案

```
用户输入ASIN
  ↓
[Layer 1] 免费HTTP抓取（fetch + DOMParser 页面结构解析）
  ├─ 成功 → 解析JSON-LD + HTML评论结构
  └─ 失败（CAPTCHA/403/429）
      ↓
[Layer 2] 代理池重试（IPIPGO 入门版 ¥30/月）
  ├─ 成功 → 同样解析流程
  └─ 失败
      ↓
[Layer 3] 备用API通道（Rainforest API，按次计费 $0.01/次）
  ├─ 成功 → 返回结构化数据
  └─ 失败
      ↓
返回"该ASIN暂时无法分析，请稍后再试"
```

**关键设计原则**：
- Layer 1 自动降级：每个 ASIN 免费抓取最多 3 次，3 次均失败才走 Layer 2
- 成功率 >= 70% 的 ASIN 继续用 Layer 1，否则标记为"高反爬"走 Layer 2
- Layer 3 是最后保险，仅当 Layer 1+2 均失败才触发
- **每层独立统计成功/失败率**，用于持续优化策略

### 1.3 评论解析技术细节

**Amazon 评论页 URL 格式：**
```
https://www.amazon.com/product-reviews/{ASIN}/
https://www.amazon.com/product-reviews/{ASIN}/ref=cm_cr_dp_d_show_all_btm?ie=UTF8&reviewerType=all_reviews
```

**需提取的结构化字段：**

| 字段 | 提取方式 | 选择器参考 | 说明 |
|:----|:---------|:----------|:----|
| 评论标题 | DOM选择器 | `[data-hook="review-title"]` | 每条评论的标题 |
| 评论正文 | DOM选择器 | `[data-hook="review-body"] span` | 用户撰写内容 |
| 评分(1-5星) | DOM属性解析 | `i[data-hook="review-star-rating"]` → aria-label | 提取"4.0 out of 5 stars"中的4.0 |
| 评论日期 | DOM选择器 | `[data-hook="review-date"]` | 发布时间（"Reviewed in the United States on July 15, 2026"）|
| 变体信息 | DOM选择器 | `.a-row.a-spacing-mini` 中"Color: Black" | 颜色/尺码（如果显示）|
| VP标签 | DOM含"Verified Purchase" | `.a-row` 含 `.a-icon-verified` | 已验证购买标记 |
| 图片/视频 | DOM属性 | `img.review-image-tile` → src | 含多媒体的评论 |
| 评论者 | DOM选择器 | `.a-profile-name` | 用户名 |

**JSON-LD 结构数据（优先解析）：**
Amazon 评论页 HTML 头部通常嵌入 JSON-LD 结构化数据（`<script type="application/ld/json">`），包含所有评论的结构化信息。优先解析 JSON-LD，JSON-LD 无数据时才走 DOM 解析。

### 1.4 反爬规避策略

| 策略 | 实现方式 | 成本 | 优先级 |
|:----|:--------|:----|:------|
| IP轮换 | 代理池轮换，每次请求换IP | ¥30-80/月 | P0 |
| User-Agent轮换 | 50+常见浏览器UA随机切换 | ¥0 | P0 |
| 请求间隔控制 | 3-5秒/请求，模拟人类行为 | ¥0（时间成本） | P1 |
| Cookie持久化 | 部分页面需登录态，手动登录一次存Cookie | ¥0 | P2 |
| Headers随机化 | Accept/Accept-Language/Accept-Encoding随机打乱 | ¥0 | P1 |
| Referer伪装 | 从Amazon搜索结果页跳转而非直接访问 | ¥0 | P1 |
| 爬取时间分布 | 错开高峰时段，均匀分布 | ¥0 | P2 |
| 请求失败重试 | 503/429错误后等待30秒重试（最多2次） | ¥0 | P0 |

### 1.5 Cloudflare Workers 爬虫实现要点

**在 CF Workers 环境下实现评论爬虫的注意事项：**

**✅ 可行：**
- `fetch()` API 原生支持（Workers 的核心能力）
- `HTMLRewriter` 流式解析 HTML（低内存、高效率）
- KV 做请求频率限制计数器（毫秒级写入）
- R2 缓存已爬取的评论原始 HTML

**⚠️ 注意事项：**
- Workers 的 IP 池有限（CF 边缘节点 IP），单纯用 Workers 直连 Amazon 很容易触发 CAPTCHA
- **必须配合代理层**：Workers fetch → 代理 → Amazon
- 单次 Worker 执行时长 ≤ 30 秒（免费用户 10ms/请求，付费用户 30s）
- 单次 ASIN 抓取 300 条评论可能需要多个请求（分页），需控制总时长

**最佳实践：**
```typescript
// CF Workers 下的爬虫核心流程

    headers,
    redirect: 'follow',
  })

  return reviews
}
```

## 第二章：DeepSeek 分析 Prompt 框架

ReviewIQ 核心价值在 **AI 分析深度**，不是普通"情感分析"（正/负面），而是 **5 层递进分析**。

### 2.1 核心分析引擎架构

```
输入：300条评论的原始文本列表（最多）
  ↓
Layer 1: 情感分类
  每条评论打标签：positive / neutral / negative / mixed
  输出：情感分布饼图 + 各情感占比
  ↓
Layer 2: 关键词提取与聚类
  提取高频名词/动词/形容词（去停用词）
  聚类为：品质/尺寸/物流/客服/使用体验/包装/价格/安装/外观/功能 10 大类
  输出：关键词云 + 词频排序表 + 情感关联词
  ↓
Layer 3: 根因分析（时间序列）
  如果评论按日期分段（最近30天 vs 前30天）→ 对比情感变化
  识别"差评激增"的关键变化点 + 归因
  输出：变化归因报告（"过去7天差评率从12%升至22%，主要因包装破损投诉增加3倍"）
  ↓
Layer 4: 竞品对标（可选）
  同一分析维度对比 我方 vs 竞品A vs 竞品B
  输出：对比雷达图 + 差距分析 + 优劣势对比
  ↓
Layer 5: Actionable 建议（核心差异化）
  基于根因分析 → 3-5 条具体改进建议
  输出："优化说明书第3-5步配图" 而不是 "改善说明书"
```

### 2.3 Token 消耗估算

| 项目 | Token数 | 说明 |
|:----|:-------:|:----|
| System Prompt | ~2,000 | 分析指令 + 输出格式定义 |
| 300条评论（平均每条50 tokens） | ~15,000 | 按最多300条中位算（实际可能从30到300条不等）|
| 分析输出 | ~2,000 | 结构化 JSON 报告 |
| 竞品对比（可选） | ~+12,000 | 额外 300 条竞品评论的等效输入 |
| **单次基础分析总计** | **~19,000 tokens** | 无竞品、无时间序列深度分析 |
| **含竞品对比** | ~31,000 tokens | |
| **含深度时间序列** | ~25,000 tokens | 每条评论标注日期、多段时间对比 |
| **完整 5 层分析** | ~35,000 tokens | 含竞品 + 时间序列 + Actionable |

**成本测算**：
- DeepSeek V4 Flash 约 ¥0.0003/1k tokens（输入），¥0.00079/1k tokens（输出）
- 单次基础分析（19k tokens）≈ ¥0.0057（输入）+ ¥0.0016（输出）≈ **¥0.0073**
- 含竞品分析（31k tokens）≈ ¥0.0093 + ¥0.0016 ≈ **¥0.011**
- 完整 5 层（35k tokens）≈ ¥0.0105 + ¥0.0016 ≈ **¥0.012**
- **即使完整分析，单次成本也不到 ¥0.02**

**为什么比之前估算更低？**
- DeepSeek V4 Flash 缓存命中率高（相同 ASIN 频繁分析时，输入 tokens 可能命中缓存折扣）
- ReviewIQ 的实际 Prompt 长度（~2k system + ~6k user）比预想的短——评论本身是最大开销

### 2.4 缓存策略

| 缓存层 | 缓存键 | TTL | 命中场景 |
|:------|:------|:---:|:--------|
| 评论原始数据 | `reviews:{asin}:{platform}` | 24h | 同一 ASIN 24h 内重复请求 |
| 分析报告 | `report:{asin}:{platform}:{has_competitor}` | 6h | 同一 ASIN 短时间多次查看报告 |
| 代理回退标记 | `proxy_fallback:{asin}` | 永久标记 | 标记为"高反爬"的 ASIN 直接走代理池 |

**实现要点**：
- 使用 CF KV 或 D1 表做缓存（KV 读性能好，D1 适合存储报告正文）
- Cache Key 需包含平台（同一产品在 Amazon 和 Walmart 的数据不同）
- 报告缓存 + 评论源数据缓存分离：有用户重新请求时，先检查评论源是否过期
- 过期策略 + 强制刷新：用户手动点击"重新分析"时忽略缓存

### 2.6 离线分析模式（可选扩展）

对于 **大量 ASIN 批量分析** 场景（而不是单次 Web 请求），可以：
1. Worker 分析请求 → 推送到 R2/队列 → Durable Object 持久化
2. DeepSeek API 异步分析 → 结果写入 D1
3. 用户稍后回来查看报告

**适用场景**：Enterprise 用户一次性上传 100 个 ASIN 进行分析

## 第七章：留存体系设计

### 7.1 新手引导流程

```
用户注册成功
  ↓
Step 1: 欢迎弹窗 + 1 分钟产品介绍动画（"3步了解你的产品评论"）
  ↓
Step 2: 引导输入第一个 ASIN（提供 5 个示例 ASIN 供选择，来自不同品类）
  ├─ B0XXXXXXXX（户外运动）
  ├─ B0YYYYYYYY（厨房用品）
  ├─ B0ZZZZZZZZ（电子产品）
  ├─ B0WWWWWWWW（家居装饰）
  └─ B0VVVVVVVV（宠物用品）
  ↓
Step 3: 等待分析结果（展示进度条 + "正在爬取评论…" → "AI 正在分析…" → "生成报告…"）
  ↓
Step 4: 展示报告（引导点击各模块：情感分布 → 关键词 → 建议）
  ↓
Step 5: 注册成功祝贺 → "首月 $1" 限时弹窗（72h 内有效）
  ↓
目标：用户完成第一次分析，激活率 ≥ 60%
```

**示例 ASIN 设计思路**：
- 挑 5 个跨品类 ASIN，确保评论数 50-800 条之间
- 每个品类至少 1 个（让不同背景的用户都能找到自己熟悉的品类）

| W2 | ≥ 100 次/周 |

| Month 3 | ≥ 1,500 次/周 |

### 8.2 核心指标追踪

| 月留存率（Core）| ≥ 50% | < 30% | 每月 |
| NPS | ≥ 40 | < 20 | 每月 |
| 平均分析耗时 | < 10s | > 20s | 实时 |
| 爬虫成功率 | ≥ 95% | < 80% | 实时 |
| API 错误率 | < 1% | > 5% | 实时 |
| 用户引荐率 | ≥ 5% | < 1% | 每周 |
| 邮件打开率 | ≥ 30% | < 15% | 每周 |

### 8.3 收入里程碑

| 里程碑 | 条件 | 预期时间 |
|:------|:-----|:--------:|
| PMF 验证 | 周留存 ≥ 40% + NPS ≥ 40 | Month 1 |
| 盈亏平衡 | MRR > ¥3,000（≈5-6 付费用户）| Month 1-2 |
| Phase 2 启动 | MRR > ¥15,000（≈25 付费用户）| Month 2-3 |
| 全面爆发 | MRR > ¥50,000（≈85 付费用户）| Month 4-6 |

**MRR 增长模型：**
```
假设：
- 月注册 200 人（上线稳定后）
- 注册→分析率 50% = 100 活跃用户
- 分析→付费率 10% = 10 付费用户/月
- ARPU ≈ $15（混合 Free/Starter/Pro）

Month 1: 10 付费用户 → MRR ≈ $150 ≈ ¥1,050
Month 2: 20 付费用户 → MRR ≈ $300 ≈ ¥2,100（累加，含留存+新付费）
Month 3: 35 付费用户 → MRR ≈ $525 ≈ ¥3,675
Month 6: 85 付费用户 → MRR ≈ $1,275 ≈ ¥8,925
```

### 9.2 退出条件

**暂停条件（满足任意一条：）**

1. **Week 4 结束，注册用户 < 50** → PMF 未验证，暂停产品投入
2. **Week 4 结束，爬虫成功率 < 60%** → 技术路线不可行，重新评估
3. **Month 2 结束，MRR < ¥1,000** → 商业模式未跑通
4. **连续 2 周，注册→分析转化率 < 15%** → 产品不行
5. **Amazon 大规模反爬导致完全无法获取评论（被起诉 / 封锁）** → 法律风险

**放弃条件（满足任意一条：）**

1. **Month 3 结束，MRR < ¥2,000** → 投入产出比不划算
2. **团队投入资源被更优先项目抢占** → 资源重新分配
3. **竞品以更快速度实现了同样的跨平台功能** → 先发优势丧失
