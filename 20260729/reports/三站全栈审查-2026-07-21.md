## A. 认证层 (auth)

### A1. Token 生成 → OK ✅
- **sellerai**: `E:\QClaw\Work-QClaw\sellerai-frontend\app\api\auth\verify-code\route.ts:119-122` — `sha256(token)` 后存入 `auth_tokens` 表
- **pick**: `E:\QClaw\Work-QClaw\pick-frontend\app\api\auth\verify-code\route.ts:119-122` — 同 sellerai
- **reviewiq**: JWT 模式，`signToken()` 使用 HMAC-SHA256，存储在 `user_quotas` 表。不存 token hash。

### A2. Token 验证 → OK ✅
- **sellerai** `generate-listing`: `resolveBearerToken()` 在所有 Bearer 路径中校验 sha256 hash
- **pick** `analyze`: `pick-frontend\app\api\pick\analyze\route.ts:28-36` — sha256 hash lookup
- **reviewiq** `analyze`: `verifyToken()` JWT 签名验证

### A3. Token 过期 → OK ✅
- 三站均使用 `AND expires_at > datetime('now')` 检查 `auth_tokens` 过期
- reviewiq JWT: `verifyToken()` 中检查 `payload.exp < Math.floor(Date.now() / 1000)`

### A4. 跨站认证 → OK ✅
- 三站共享 `sellerai-db`，`auth_tokens` 表是同一个。同一个 SHA-256 hashed token 在三站均可通过 `auth/me` 验证。
- `sellerai`/`reviewiq` `auth.ts` 均使用 `sellerai_auth_token` key 存储 token，所以技术上一个站登录后，切换到另一个站时 `checkSession()` 可用。

### A5. JWT Secret → ISSUE ⚠️
- `pick-frontend\wrangler.jsonc:15` — `JWT_SECRET: "pick-jwt-prod-20260720"` 硬编码在 `vars` 中
- `reviewiq-frontend\wrangler.jsonc:16` — `JWT_SECRET: "reviewiq-jwt-prod-20260720-m8xk9v"` 硬编码在 `vars` 中
- `vars` 是 Cloudflare 环境变量，非 secrets。可通过 dashboard 或 API 读取。
- **建议**: 迁移到 `wrangler secret put JWT_SECRET`

### A6. Session 清理 → ISSUE ⚠️
- 三站均无定期清理过期 `auth_tokens` 的机制。D1 不支持 cron trigger。
- 过期 token 将无限累积在 `auth_tokens` 表中。
- `auth_codes` 同理 — 已使用 (`used=1`) 的 code 不会删除。

### A7. 登出 → OK ✅
- 三个 `lib/auth.ts` 的 `logout()` 均执行 `localStorage.removeItem(TOKEN_KEY)` + `localStorage.removeItem(USER_KEY)`
- reviewiq 还调用 `window.location.reload()`

### B10. 门控 fail-closed → FATAL 🔴
- **所有三站** `auth/me/route.ts` 中 `JSON.parse(user?.product_access || '["listing"]')` — 无 try-catch
- 如果 `product_access` 列包含非法 JSON（如同步破损、手动修改），`JSON.parse` 抛异常 → 整个 `/api/auth/me` 返回 500，用户无法登录
- **文件**: 
  - `sellerai-frontend\app\api\auth\me\route.ts:50`
  - `pick-frontend\app\api\auth\me\route.ts:50`
  - `reviewiq-frontend\app\api\auth\me\route.ts:43,72`

### B11. 默认值安全 → OK ✅
- `sellerai-frontend\migrations\0004_multi_product_support.sql:7` — `product_access TEXT NOT NULL DEFAULT '["listing"]'`
- 新用户自动获得 listing 权限

### B12. 绕过风险 → OK ✅
- `product_access` 仅从 DB 读取，不可由前端传入。无法通过修改请求参数绕过。
- 无 API 端点允许用户修改自己的 `product_access`。

## C. 配额层 (quota/rate-limit)

### C13. 日配额重置 → FATAL 🔴 (reviewiq)
- **sellerai**: `lib/quota.ts:104-107` — `quota_date !== today` 时重置 ✅
- **reviewiq**: `app/api/reviewiq/analyze/route.ts` — 读取 `user_quotas` 中的 `analyses_used` 和 `reset_at`，但从未检查 `reset_at` 是否过期并重置！配额只增不减。
- **FATAL**: reviewiq 的 `user_quotas` 表从未重置 `analyses_used`。一旦用完每日/每月配额，永不恢复。

### C14. 配额递减 → OK ✅
- **sellerai**: `checkQuota()` 中 `quota_remaining = quota_remaining - 1` 使用条件 UPDATE 原子操作
- **reviewiq**: `analyze/route.ts:135` — `analyses_used = analyses_used + 1` 在分析完成后

### C15. 配额检查时序 → OK ✅ (sellerai), FATAL 🔴 (reviewiq)
- **sellerai**: 先检查 `remaining <= 0`，再执行条件 UPDATE。使用 `changes` 计数防御 TOCTOU。
- **reviewiq**: `analyze/route.ts:76-83` — 先读取 `used`（`if (limit !== -1 && used >= limit)`），之后在第 135 行才扣减。两者之间无锁 → **经典 TOCTOU 竞态条件**。

### C16. 并发超量 → ISSUE ⚠️ (sellerai)
- **sellerai** 使用条件 UPDATE `WHERE quota_remaining > 0 AND quota_date = ? AND subscription_status = 'free'` + 检查 `meta.changes`，部分缓解了 TOCTOU。
- 但 D1（基于 SQLite）不支持 SERIALIZABLE 隔离级别，两个并发请求读到剩余 1 后，条件 UPDATE 可能都返回 changes=0（都认为没插槽了），导致该扣减却被拒的假阴性问题。
- 实际影响：极低概率下用户可能用满配额但被拒绝一次。

### C17. 配额上限 → ISSUE ⚠️
- **sellerai**: `FREE_DAILY_LIMIT = 3`, trial=9999, active/cancelled=999 ✅
- **pick**: `lib/quota/engine.ts` 定义 trial=999, starter=50, pro=-1，但实际 analyze 端点在 `route.ts:56` 使用硬编码 trial=5, paid=20。quota/engine.ts 完全未被调用。
- **reviewiq**: `lib/quota/engine.ts` 定义 trial=999, pro=100。analyze 端点调用 `getPlanLimit(quotas.plan)`

### C18. ReviewIQ 配额 → FATAL 🔴
- `app/api/reviewiq/analyze/route.ts:135` — `SET analyses_used = analyses_used + 1` 永远递增
- `user_quotas.reset_at` 字段从未被检查。`verify/route.ts:94` 初始化为 `datetime('now', '+1 day')` 但在 analyze 中完全忽略
- 用户用完试用期后配额永不恢复

## F. D1 数据库

### F30. 共享 D1 冲突 → OK ✅
- 三站共享 `sellerai-db`，表名无冲突：
  - `users`, `licenses`, `payment_events`, `generation_logs`, `auth_codes`, `auth_tokens`, `analysis_cache`, `user_quotas`
- 所有表共享同一 D1 实例 ✅

### F31. Migration 冲突 → FATAL 🔴
**这是本次审计中最严重的问题。** 三站各自管理 migrations 目录但共享同一个 D1：

| 站点 | Migration 文件 | 关键差异 |
|:--|:--|:--|
| **sellerai** | 0001-0004 | 0004 添加 `product_access` 列到 users |
| **pick** | 0001-0003 仅 | **缺失 0004** — 无 product_access 列 |
| **reviewiq** | 0001-0007 | 0004-0007 与 sellerai 完全不同 |

**致命冲突**:

1. **`reviewiq-frontend\migrations\0007_cleanup_and_ensure.sql:10`** — `DROP TABLE IF EXISTS users;` 然后 CREATE TABLE users 使用 `id TEXT PRIMARY KEY` 替代 `visitor_id TEXT PRIMARY KEY`。
   - 一旦 reviewiq 执行 0007 迁移，**sellerai 和 pick 的所有用户数据被清空**。
   - 新表结构不兼容：sellerai 使用 `visitor_id`，reviewiq 使用 `id`。

2. **`pick` 缺失 0004**：
   - product_access 列不存在时，JSON.parse(user?.product_access) 返回 undefined → 所有 pick 用户默认只能访问 listing
   - 即使付费了 Pro/Max，pick 仍返回 403

3. **reviewiq 0004 与 sellerai 0004 冲突**：
   - reviewiq: `analysis_cache` 表（asin TEXT PRIMARY KEY）
   - sellerai: `analysis_cache` 表（id INTEGER PRIMARY KEY AUTOINCREMENT, asin TEXT NOT NULL UNIQUE）
   - 哪个先执行就创建哪个，另一个将失败或被跳过

### F32. 外键 → FATAL 🔴
- `generation_logs` 表（0001_init.sql）: `FOREIGN KEY (visitor_id) REFERENCES users(visitor_id)`
- reviewiq 0007 重建的 users 表使用 `id TEXT PRIMARY KEY` 而非 `visitor_id` → **外键约束失效**
- 如果 0007 先执行，0001 的 `CREATE TABLE generation_logs` 因 FOREIGN KEY 引用不存在的 `users(visitor_id)` 列而失败

### F33. 索引 → OK ✅
- `idx_users_email`, `idx_users_license` ✅
- `idx_auth_tokens_email` ✅ (但主查询按 `token` 列即 PRIMARY KEY)
- `idx_auth_codes_email` ✅
- `idx_analysis_cache_asin` ✅
- `idx_user_quotas_user_id` ✅

## G. Webhook (Gumroad)

### G34. 签名验证 → OK ✅
- `sellerai-frontend\app\api\gumroad-webhook\route.ts:17-32` — `verifySignature()` 使用 `crypto.subtle.verify("HMAC", ...)` + SHA-256
- 如果 `GUMROAD_WEBHOOK_SECRET` 未设置 → 返回 500（fail-closed） ✅
- `GUMROAD_WEBHOOK_SECRET` 不在 wrangler.jsonc vars 中，需要单独设置 ✅

### G35. 幂等性 → ISSUE ⚠️
- `payment_events` 表无 **UNIQUE** 约束在 `gumroad_sale_id` 上
- 重复 webhook 事件会创建重复的 `payment_events` 行
- `licenses` 表有 `license_key PRIMARY KEY` + `ON CONFLICT(license_key) DO UPDATE`，所以许可证侧是幂等的 ✅

### G36. PRODUCT_MAP 映射 → FATAL 🔴
- `sellerai-frontend\app\api\gumroad-webhook\route.ts:81-93`:
  ```typescript
  const PRODUCT_MAP: Record<string, string[]> = {
    "listing-only-product-id": ["listing"],
    "pro-product-id": ["listing", "pick"],
    "max-product-id": ["listing", "pick", "reviewiq"],
    "kajyx": ["listing", "pick", "reviewiq"],
  };
  const access = PRODUCT_MAP[productId] || ["listing", "pick", "reviewiq"];
  ```
- **所有 5 个 product_id 都是占位符**（待填入）
- **兜底默认值 `["listing", "pick", "reviewiq"]`**：任何未知 product_id（如新创建的 Gumroad 产品）都授予全部三个产品的访问权限
- **业务风险**：如果有人花 $19.90 买 Listing Only，但 Gumroad 传了一个不在 MAP 中的 product_id → 获得全部产品访问权

### G37. 兜底逻辑 → FATAL 🔴
- 第 93 行的 `|| ["listing", "pick", "reviewiq"]` 应改为 `|| ["listing"]`（最低权限兜底）
- 或当 product_id 未知时，记录错误并返回 400，拒绝处理
