# SellerAI 联盟分佣财务核算报告

> 角色：财务/成本部 · 成本核算专家
> 日期：2026-07-16
> 对象：营销部提案「Gumroad 联盟 30% 终身分佣（recurring lifetime）」
> 结论基调：**独立核算，给财务背书或否决。**

---

## 0. 结论摘要（先看这个）

| 项目 | 结论 |
|------|------|
| 真实净利率（30% 终身，正价 $19.9） | **≈ 54%**（约 **$10.7/订阅/月** 净留存，非增长专家说的 $7.9） |
| 真实净利率（创始价 $14.9） | **≈ 53%**（约 **$7.9/订阅/月** 净留存） |
| 30% 佣金比例本身 | 扛得住（单月不亏，且有厚利） |
| 「终身 / lifetime」结构 | **否决。** 不可逆转的长期可变成本，永久侵蚀 LTV 与毛利，且对预营收微现金项目是危险杠杆 |
| 增长专家 "$7.9/单净赚" 口径 | **错误**：公式 `57%×70%` 重复扣减了 30% 佣金（affiliate 已含在 57% 内又乘 70% 再扣一次），数字不可作财务依据（其方向对、数值偏低） |
| **财务最终推荐** | **否决 30% 终身 → 改为 20% 非终身（仅首 12 个月 recurring）**；launch 冲量期可限时 90 天给 25%，绝不给终身 |

> 一句话：比例能扛，终身不能要。把"30% 终身"砍成"20% 首年"，既保住冷启动让利空间，又锁住长期 LTV。

### 2.3 API 成本敏感性（增长专家完全漏算的变量成本）

API 按「生成次数」计，不是按订阅计。需对单订阅月均生成次数做假设：

| 单订阅月生成次数 | 月 API 成本(¥) | 月 API 成本($) | 占 $19.9 毛额 |
|------------------|----------------|----------------|---------------|
| 50 次（轻度） | ¥0.30 | $0.04 | 0.2% |
| 150 次（中度，基准） | ¥0.90 | $0.13 | 0.6% |
| 500 次（重度卖家） | ¥3.00 | $0.42 | 2.1% |

**结论**：即便重度卖家（500 次/月），API 成本也仅 ~2% 毛额，对 54% 净利率几乎无威胁。**但它被增长专家完全漏算**，必须入账；且当前 DeepSeek 余额仅 ¥22.49（约可支撑 ~3,700 次生成），若 10 个付费订阅各跑 150 次/月 = 1,500 次/月，余额仅够 ~2.5 个月——近 3 个月有 API 现金断档风险，需提前充值（非分佣问题，但属同口径成本警示）。

## 3. 增长专家口径核实：`$19.9 × 57% × 70% ≈ $7.9`

**裁定：该口径不成立，数字不可作财务依据。**

反推其逻辑：
- `70%` = (1 − 30% 联盟佣金)，意图在毛额上再扣一次佣金。
- `57%` 若代表「扣完 Gumroad+手续费+佣金后的净留存」，则应为 1 − 10% − 4.4% − 30% = **55.6%**（≈其 57%，四舍五入）。

**错误点：重复扣减。** `57%` 已经把 30% 联盟佣金扣掉了，后面再 `×70%` 等于把佣金**扣了第二次**。正确写法应是 `$19.9 × 55.6%`（不再乘 70%），即净留存 ≈ $11.06（扣 FX/API 前），或 $10.7（扣后）。

**数字影响**：
- 增长专家声称净留存 **$7.9**（= 毛额 39.9%）。
- 真实净留存 **≈ $10.7**（= 毛额 53.8%）。
- 其数值**偏低约 $2.8/月（低 ~14 个点）**——即"暴利"结论方向对，但算账方式错、且把利润算少了。不能引用其公式，但可确认：即便按真实费率，单月仍厚利。

**附：增长专家另一处含糊**——"毛利 ~87%、单次成本 <¥0.01" 是把「仅 API 成本」当毛利，完全没算 Gumroad 平台费(10%)+支付处理(~4.4%)+汇率损耗(2%)+联盟佣金(30%)。真实经营毛利率（含联盟 30% 终身）是 **~54%**，不是 87%。

## 4. 退款 / 拒付风险（是否倒亏）

| 风险 | 机制 | 是否倒亏 | 备注 |
|------|------|----------|------|
| 客户首月退款 | Gumroad 退全款给用户，平台费通常退还；**联盟佣金是否 clawback 待核实** | 若佣金已发出且不追回 → 我们白付佣金 + 损失处理费 → **单期微亏** | 需确认 Gumroad 退款时自动追回 affiliate commission |
| 订阅中途退款（已付数月的用户） | 退款通常限最近一期或按比例；已付历史期佣金处置看政策 | 同上，取决于 clawback | 终身制下，长留存用户退款冲击更大 |
| 拒付 / Chargeback | 发卡行争议，Gumroad 收 ~$15 争议费 + 全款退还 | **确定倒亏**（损失 = 该期收入 + $15 + 已付佣金） | 联盟流量质量参差，chargeback 概率高于自然流量，须计入 CAC/坏账预备 |
| 终身制的特殊放大 | 佣金按月已发给联盟，若某期退款而佣金不追回，则"为已退回的收入付佣金" | **结构性小亏** | 非终身制可大幅降低此敞口 |

**财务判断**：单笔退款本身不会让整单崩盘（毛利率 54% 有缓冲），但**终身 recurring + 退款 clawback 政策不明**叠加，会在 chargeback 与"已付佣金不退"情景下产生确定性或准确定性亏损。上线前必须向 Gumroad 书面确认：①订阅退款是否自动追回联盟佣金；②拒付费用承担方。

## 5. 终身 vs 限期：LTV 侵蚀对比

核心问题：30% 终身 = 对我们 **100% 的 recurring 收入永久征收 30%**。产品越留得住客，我们亏得越多，且**不可逆转、不可重谈**。

以正价 $19.9、单订阅为例（净留存按 $10.7/月、去佣金后月净 $16.5 计）：

| 用户生命周期 | 方案 | 累计给联盟 | 累计净留存(我们) |
|--------------|------|-----------|------------------|
| 12 个月（平均留存假设） | 30% 终身 | $71.6 | $128.6 |
| 12 个月 | 20% 首年(限期) | $47.8 | $152.4 |
| 24 个月（好留存） | 30% 终身 | **$143.3** | $257.3 |
| 24 个月 | 20% 首年(限期) | $47.8 | **$326.9** |
| 24 个月差额 | 限期 vs 终身 | 少付 $95.5 | **多留 $69.6/用户** |

**毛利率视角**：
- 无联盟佣金时，经营毛利率（扣平台+处理+汇率+API）≈ **84%**。
- 30% 终身把毛利率从 84% 压到 **54%**——**永久砍掉 30 个点**。
- 若改为 20% 首年（非终身），首年毛利率 ~57%，**第 13 个月起回升至 84%**。

**战略敞口**：现在产品零营收、现金极薄（累计仅花 ¥103），一旦签下"终身 30%"，等于把未来所有留存收益的固定 30% 永久性让渡出去。若产品变好、留存拉长，这部分让利会**复利放大**且无法回收——这是比单月亏损更危险的"期权价值流失"。

## 6. 财务最终推荐值 + 理由

### 裁定
**否决「30% 终身分佣」。** 比例本身可扛（单月净利率 ~54%，不亏），但「终身 / lifetime」结构与当前「预营收 + 微现金 + 退款政策未核实」状态不匹配，构成不可逆的长期 LTV 侵蚀与杠杆风险。

### 推荐方案
| 维度 | 推荐值 | 理由 |
|------|--------|------|
| 佣金比例 | **20%**（标准 SaaS 联盟档） | 市场常态 20%；30% 仅适合限时 launch 冲刺。20% 下联盟仍可从 $19.9 用户赚 $3.98/月×12 = $47.8，对种子联盟有足够吸引力 |
| 期限 | **非终身，仅首 12 个月 recurring** | 保住冷启动让利，同时第 13 月起毛利率回升至 84%，锁住 LTV |
| Launch 限时加码 | 可选 **25%，限前 90 天** | 若营销坚持用高佣抢种子联盟，把 30%→25% 且只给 90 天窗口，绝不写进终身 |
| 底线红线 | **任何情况下不签 lifetime** | lifetime 不可逆转、不可重谈，对预营收项目是危险杠杆 |

### 给营销部的落地建议
1. 用「20% × 首 12 个月」作为标准联盟条款对外宣讲；前 90 天可挂"launch 25%"限时徽章冲量。
2. 上线前用真实 Gumroad 账号跑一笔 $19.9 订阅，实测：**实际平台费、处理费、USD→CNY 到账额、退款时佣金是否 clawback**——把本报告「待核实」项全部坐实后再签联盟合同。
3. 把 API 成本（按用量）与 chargeback 预备（建议按营收 1–2%）纳入月度 P&L，别再只算"87% 毛利"。
4. 当前 DeepSeek 余额 ¥22.49 仅够约 2.5 个月中等用量，扩张前先充值，避免服务断档。
