## 七、致命问题 Top 5

### 🔴 #1 分析API无认证（严重程度：致命）

- **文件**：`app/api/reviewiq/analyze/route.ts`
- **行号**：第6行起（整个POST handler）
- **问题**：API route完全没有JWT验证。前端虽然发送Authorization头，但后端从未读取或验证它。任何人都可以无限次调用分析API，消耗DeepSeek API额度。
- **修复方案**：在POST handler开头添加JWT验证中间件，调用 `verifyToken()` 检查Authorization header，未登录返回401。
```typescript
const authHeader = request.headers.get('Authorization') || '';
const token = authHeader.replace('Bearer ', '');
const payload = await verifyToken(token);
if (!payload) {
  return NextResponse.json({ error: 'Authentication required' }, { status: 401 });
}
```

### 🔴 #2 JWT Secret硬编码fallback（严重程度：致命）

- **文件**：`lib/auth/jwt.ts`
- **行号**：第2行
- **问题**：`const SECRET_KEY = 'reviewiq-jwt-secret-2026'` — 如果CF Worker环境变量未设置JWT_SECRET，将使用此硬编码字符串。任何人拿到源码（开源）即可用此secret伪造任意用户的JWT token。
- **修复方案**：
  1. 删除硬编码fallback，改为强制要求环境变量
  2. 在CF Workers dashboard设置JWT_SECRET环境变量
  3. 在signToken/verifyToken调用前检测是否设置了JWT_SECRET

### 🟡 #3 数据库Migration冲突（严重程度：严重）

- **文件**：`migrations/0001_init.sql` + `migrations/0006_users.sql`
- **问题**：
  - 0001创建`users(visitor_id PRIMARY KEY)`，0006创建`users(id PRIMARY KEY)` —— 两套完全不同的schema
  - 当前本地D1只有0001版本的users表，0006的CREATE IF NOT EXISTS会静默失败
  - `auth_codes`、`user_quotas`、`auth_tokens` 三张表在本地DB中完全不存在
- **修复方案**：
  1. 清空/迁移本地D1数据
  2. 删除0001_init.sql中的users/licenses/payment_events/generation_logs定义（保留到归档目录）
  3. 创建新的0007 migration清理旧SellerAI表
  4. 确保0003-0006 migration在本地和远程DB都已执行

### 🟡 #4 配额系统碎片化（严重程度：严重）

- **文件**：`app/api/quota-status/route.ts`、`lib/quota.ts`、`lib/quota/engine.ts`
- **问题**：同时存在两套配额系统：
  - SellerAI旧系统：visitor_id + licenses表 + 3次/天
  - ReviewIQ新系统：user_quotas表 + JWT + plan-based
  - 分析API既不检查旧配额也不检查新配额
- **修复方案**：
  1. 分析API添加配额检查（读取user_quotas表）
  2. 移除/重构 quota-status API 以使用JWT认证
  3. 删除 `lib/quota.ts` 中的旧配额逻辑

### 🟡 #5 重复/冲突的verify端点（严重程度：中等）

- **文件**：`app/api/auth/verify/route.ts` + `app/api/auth/verify-code/route.ts`
- **问题**：
  - verify使用JWT方案，verify-code使用旧token-hash方案
  - `POST /api/auth/verify` 和 `POST /api/auth/verify-code` 两个路由共存
  - 前端调用了verify（JWT），但verify-code也能被外部调用
  - verify-code使用旧SellerAI users表结构（visitor_id），与新的id-based users不兼容
- **修复方案**：
  1. 删除 `app/api/auth/verify-code/route.ts` 及其 `.bak` 文件
  2. 确保所有auth相关路由统一使用JWT + user_quotas
