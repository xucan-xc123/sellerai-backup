## 检查项 3：Gumroad webhook 漏洞
- **结论：PASS** ✅（有 2 处可改进项）
- **详情：**
  - ✅ **签名验证正确**：HMAC-SHA256，使用 `X-Gumroad-Signature` header，secret 来自 `GUMROAD_WEBHOOK_SECRET` 环境变量。secret 未配置时拒绝所有请求（返回 500，正确）。
  - ✅ **Tier/variant 解析**：`TIER_ACCESS` 字典包含 listing/pro/max/annual 四个 tier，用 `variantLabel.includes(tier)` 做 partial match（容错性好，例如 "Max ($69.90)" → 匹配 max）。无 variant 时回退到 `product_id` 映射。
  - ✅ **空 variants 处理**：`variantsRaw` 空字符串 → `variantLabel` 空字符串 → 不进入 for 循环 → `access = ["listing"]` 合理 fallback。
  - ✅ **取消（cancellation）**：只改 `licenses.status='cancelled'` 和 `users.subscription_status='cancelled'`，不删权限，用户能用完当前周期。正确。
  - ✅ **退款/争议（refund/dispute）**：设置 `licenses.status='revoked'` 和 `users.subscription_status='expired', quota_remaining=0`。正确。
  - ✅ **event type 覆盖**：处理了 sale、cancellation、refund、dispute。其他事件 default 分支只打 log，不报错（200 OK）。
  - ⚠️ **可改进 1**：cancellation 的 `UPDATE users` 用的是 `WHERE id = (SELECT user_id FROM licenses...)`，但 `licenses` 表没有 `user_id` 列——这个 WHERE 子句永远匹配不到，实际回退为空操作。应该用 `WHERE license_key = (SELECT license_key FROM licenses WHERE gumroad_sale_id = ?)` 或通过 email 匹配。
  - ⚠️ **可改进 2**：refund/dispute 的 `UPDATE users` 同样用了 `user_id` 子查询，也是无效的。用户不会被降级。
  - **严重程度**：对 cancellation 和 refund/dispute 来说，**用户不会被正确降级**。cancellation 用户继续享有 unlimited，refund/dispute 用户也不会被 revoked。这是实际缺陷。

## 检查项 4：D1 schema 一致性
- **结论：FAIL** ❌（2 个问题）
- **详情：**
  - ✅ **migrations 对照**：
    - `0001_init.sql`：users（visitor_id, email, subscription_status, quota_remaining, quota_date, license_key, created_at, last_active_at）+ licenses（license_key, email, status, claimed_by_visitor, claimed_at, gumroad_sale_id, created_at）+ payment_events + generation_logs
    - `0002_trial.sql`：ALTER users ADD COLUMN trial_started_at / trial_ends_at
    - `0003_auth.sql`：auth_codes + auth_tokens 表
    - `0004_multi_product_support.sql`：ALTER users ADD COLUMN product_access / licenses ADD COLUMN product_id + analysis_cache + user_quotas 表
    - `0005_product_access_tier.sql`：ALTER licenses ADD COLUMN product_access + 索引
  - ❌ **问题 1 — licenses 表无 user_id 列**：Gumroad webhook 中 cancellation 和 refund 的 UPDATE 语句引用 `licenses.user_id`，但 `licenses` 表从未定义过 `user_id` 列。migrations 0001-0005 中没有任何 `ALTER TABLE licenses ADD COLUMN user_id`。这是一个 **dead SQL**——子查询永远返回空，导致取消/退款无法正确降级用户。
  - ❌ **问题 2 — users.product_access 默认值**：`0004` 中 `DEFAULT '["listing"]'` 正确。但 `quota.ts` 中的 `activateLicense()` 传入 `lic.product_access || '["listing"]'`，不依赖默认值，所以 OK。
  - ✅ **users 表 product_access 对齐**：`auth/me/route.ts` 读取 `users.product_access`，Gumroad webhook 写入 `users.product_access`，quota.ts 的 `activateLicense()` 写入 `product_access`，全部对齐。

## 检查项 7：业务逻辑缺陷
- **结论：PASS with FAIL items** ✅❌
- **详情：**

  ### 7.1 免费用户 3次/day quota 竞态
  - **结论：PASS** ✅
  - quota.ts 使用原子 UPDATE 条件：`WHERE visitor_id = ? AND quota_remaining > 0 AND quota_date = ? AND subscription_status = 'free'`，然后检查 `changes（受影响行数）`。D1 的 UPDATE 天然是原子操作，多请求并发时只有一个会成功减 1。竞态安全。

  ### 7.2 Trial 过期后是否自动降级 free
  - **结论：PASS** ✅
  - `checkQuota()` 在 status === "trial" 时检查 `isTrialExpired()`，如果过期则 UPDATE 为 `subscription_status='free'`，并返回 `FREE_DAILY_LIMIT`。`readQuota()` 也有相同逻辑。

  ### 7.3 activate-license 是否正确处理已 claim 的 license
  - **结论：PASS** ✅
  - `activateLicense()` 检查 `lic.claimed_by_visitor`：如果被其他人 claim 过且 `visitorId != claimed_by_visitor`，返回 `already_claimed` 错误。同一个 visitor 再次 claim 是幂等的（`UPDATE licenses SET status='claimed'` 重复执行无害）。

  ### 7.4 claim-license 的 email 匹配是否 case-insensitive
  - **结论：PASS** ✅
  - `claim-license/route.ts` 中 `body.email` 在进入时 `.trim().toLowerCase()` ✅
  - SQL 查询用 `lower(email) = ?`（`bind(normEmail)`）✅
  - `activateLicenseByEmail()` 也做了同样的 normalize ✅

  ### 7.5 🔴 **Gumroad webhook 中 cancellation/refund 不会生效**
  - **结论：FAIL** ❌
  - 见检查项 3 的可改进项。`UPDATE users ... WHERE id = (SELECT user_id FROM licenses WHERE gumroad_sale_id = ?)` 中的 `user_id` 在 `licenses` 表中不存在。**以下操作均无效**：
    - cancellation：用户不会被降级
    - refund/dispute：用户不会被 revoked
  - **严重性：高**。用户取消订阅或退款后仍能继续无限制使用。

### 7.6 前端无需修复的 INFO
- `ScorerWithGate.tsx` 和 `KeywordWithGate.tsx` 包裹 `LoginGate`，强制登录后使用——正确。
- `ListingChecker.tsx` 和 `ProfitCalculator.tsx` 完全免费无门控——设计如此，正确。
- `ListingGenerator.tsx` 本身无门控，但 API 端 `generate-listing` 有配额校验——正确。

### 必须修复的 bug（严重度 = 高）

**Bug 1：Gumroad webhook 取消/退款降级不生效**
- 文件：`app/api/gumroad-webhook/route.ts`
- 位置：cancellation 和 refund/dispute 分支
- 根因：SQL 中不存在的 `licenses.user_id` 列导致子查询永远返回空
- 修复方案：将 `id = (SELECT user_id FROM licenses ...)` 改为通过 `license_key` 或 `email` 匹配：
  ```sql
  -- cancellation
  UPDATE users SET subscription_status='cancelled'
  WHERE email IN (SELECT email FROM licenses WHERE gumroad_sale_id = ?)
    AND subscription_status = 'active';
  
  -- refund/dispute
  UPDATE users SET subscription_status='expired', quota_remaining=0
  WHERE email IN (SELECT email FROM licenses WHERE gumroad_sale_id = ?);
  ```

**Bug 2：D1 schema 中 licenses.user_id 列缺失**
- 文件：migrations、gumroad-webhook
- 根因：migrations 0001-0005 从未创建 `user_id` 列，但 webhook 引用了它
- 修复方案：在 migration 0005 之后增加 0006_migration 添加 `user_id` 列，或者直接用 email 关联

### 建议修复（低/中）

1. **Pricing.tsx 的 Gumroad variant 链接**：可为每个 tier 使用不同 URL 参数预选 tier，减少用户操作步骤
2. **verify-code 返回 product_access 的持久化验证**：当前 verify-code 在 return 中固定 `product_access: data.product_access || ["listing"]`。从 `auth/me` 的返回值来看这不是问题（实际权限从 DB 读），但 verify-code 应当返回真实的 product_access

### 终审结论

代码整体质量良好，架构设计合理，权限系统正确。**核心问题是 Gumroad webhook 的 cancellation/refund/dispute 降级逻辑因 SQL 中使用了不存在的列而永远无法生效**，这是一个严重的收入保护问题。建议优先修复。
